# Agent Note: 预览版手工更新提醒

状态：已实现

[English](2026-08-24-desktop-manual-preview-updates.md) | 中文

## 问题

小范围测试需要一条不会进入稳定版自动更新源的预发布通道。若应用完全不提供更新提醒，测试者就只能依赖维护者另行通知，也容易长期使用内置 Harness 已过期的版本。频繁轮询或直接打开 API 中的任意字段还会造成不必要的 GitHub 频率消耗与不安全的外部导航。

## 决策

带语义化预发布后缀的桌面打包版本使用手工 Release 提醒控制器；稳定版继续使用签名自动更新生命周期。源码构建与不受支持的架构不会查询公开仓库，用户执行菜单命令时会看到相应说明。

### 发现 Release

预览版会在启动三十秒后读取 `mintgao/dsh-desktop` 的公开 Releases API，之后每六小时读取一次，而且不携带凭据。后续请求会发送已保存的 ETag。它同时接受预览版与稳定版，忽略草稿和无关标签，并选择包含当前 arm64 或 x64 进程所需 `DSH-Desktop-Mint-<version>-<arch>.dmg` 资产的最高语义化版本。应用根据已校验的仓库与标签构造 Release URL，不信任 API 返回的外部 URL。

主进程通过 Electron 网络接口执行请求，不增加 renderer 权限或 preload bridge。当前 Release、ETag、已跳过版本、最近通知版本与一次提醒时间都会在本地 JSON 边界完成校验，并以原子替换方式写入应用 user-data 目录。无法读取或不受支持的文档会重置为默认值并记录诊断，不会阻止应用启动。

### 用户提醒与决策

每个版本首次在后台被发现时，客户端都会修改应用菜单、增加提醒徽标，并请求一次原生通知。已签名应用可以展示该通知；申请证书前的未签名预览版可能收不到 macOS 横幅，只能依赖菜单、徽标与手工命令。客户端绝不下载 DMG。点击通知或在原生对话框中选择**前往 Release 下载**会打开确切 Release 页面，显示 Mac 架构与推荐文件名，并安排 24 小时后的一次提醒。**明天提醒我**使用相同延迟。**跳过此版本**只会屏蔽该版本的后台提醒，更高版本仍可正常通知。菜单命令始终允许用户重新查看已知 Release。

后台错误只写入桌面日志。手工检查失败时会显示原生对话框，并可打开仓库的 Releases 总页。应用关闭时会取消两类定时器并关闭进程持有的通知。

### 发布与信任阶段过渡

带预发布后缀的标签会选择手工 Release 提醒。在默认的[申请证书前阶段](../process/2026-08-27-pre-certificate-unsigned-desktop-previews.zh.md)，发布工作流会构建未签名的 arm64、x64 DMG，并在标题与说明中标明缺少 Apple 信任身份；显式启用签名后，预发布标签会构建经过 Developer ID 签名与公证的 DMG。[自动上游引入](../process/2026-08-27-automatic-upstream-desktop-releases.zh.md)会在当前阶段要求的全部检查通过后公开 Pre-release，手工推送的桌面标签则创建草稿。两者都只包含这两份 DMG 与 SHA-256 校验和。校验文件记录产物基本名，因此把它与 DMG 下载到同一目录后即可运行标准校验命令，无需重建 CI 目录。生成的发布说明会标明发行版与信任阶段，提供两种架构的直达链接，解释手工替换，并记录内置 Harness 标签、提交与桌面源码提交。

预览版可以发现后续稳定版，并引导用户完成最后一次手工安装。稳定版没有预发布后缀，因此新安装的应用会切换到 `electron-updater` 生命周期。预览产物不提供 channel 元数据，也不会进入自动安装。

## 考虑过的备选方案

**要求用户关注 GitHub 或维护者消息。** 这样无需增加应用代码，却无法提供持久提醒和架构指引。原生 Release 提醒可以在保持手工安装的同时，让版本状态出现在用户工作的应用中。

**在应用内下载预览版 DMG。** 下载按钮容易被误认为稳定版自动更新路径，但安装仍然需要手工完成。打开确切 Release 页面可以把来源、校验和与说明放在一起。

**使用私有端点或内置 GitHub token。** 分发到客户端的凭据不再是秘密，要求每位用户认证又会增加无关设置。当前检查间隔配合匿名条件请求，远低于 GitHub 的公开频率限制。

**永久替代签名稳定版更新器。** 对知情预览测试者而言，手工替换可以接受，但长期的安全性与便利性都更差。版本后缀提供了确定的签名通道切换规则。

## 验证

控制器测试覆盖通知去重、24 小时一次性提醒、跳过版本隔离、手工检查结果、错误可见性、调度与关闭。API 测试覆盖 ETag、HTTP 错误、语义化排序、草稿与无关标签过滤、架构产物和确切 Release URL。偏好测试覆盖原子往返与无效文档重置。工作流测试证明预发布标签会排除自动更新产物，默认使用未签名打包，而且只在显式启用后要求签名与公证；已签名稳定标签保留更新元数据；自动与手工触发分别选择公开或草稿发布。Electron TypeScript 构建会验证原生集成。

## 后果

早期测试者无需静默下载代码即可感知版本，而且仍能发现首个已签名稳定版。申请证书前的预览版不需要 Apple 凭据，却无法验证依赖应用身份的原生能力，也可能要求明确绕过 Gatekeeper；后续签名预览版会提供用于原生验收的稳定应用身份。测试者仍须核对标签、文件名与校验和并手工替换应用。GitHub 可用性会影响后台提醒，但绝不会影响应用启动或已有 DSH 工作。维护者必须提供清晰的发布说明，不得把预览产物描述成适合无人值守安装的版本。
