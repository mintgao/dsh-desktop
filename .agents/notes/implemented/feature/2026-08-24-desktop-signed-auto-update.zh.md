# Agent Note: 由用户控制的桌面版签名更新

状态：已实现

[English](2026-08-24-desktop-signed-auto-update.md) | 中文

## 问题

自包含的 DSH Desktop 应用无法继承全局安装的 Harness 更新，独立替换其内置运行时也会破坏从源码构建应用的证明。手工替换 DMG 无法在应用内提醒用户，而未经同意就下载或重启可能中断正在运行的本地 Agent 会话。公开版本还同时包含原生 arm64 与 x64 应用，因此同一个更新源必须选择正确架构，且不能暴露仓库凭据。

## 决策

经过签名的 macOS 稳定版使用 `electron-updater` 读取 `mintgao/dsh-desktop` 的公开 GitHub Releases。更新器只接受稳定版本，绝不自动下载；除非用户明确选择，否则普通退出时也绝不自动安装。源码构建与未打包构建没有更新源，用户手工执行命令时会看到相应说明。未签名预览版使用独立的[预览版手工更新提醒](2026-08-24-desktop-manual-preview-updates.zh.md)生命周期。

### 检查与用户决策

控制器会在后端可用十秒后执行检查，此后每六小时检查一次。**DSH Desktop > Check for Updates…** 可以手工执行同一检查。发现新版本后，原生对话框会让用户选择下载、稍后处理或打开公开发布页面。下载进度显示在应用菜单、Dock 与窗口中。下载完成后会再次让用户选择重启并安装、下次正常退出时安装或稍后处理。所有路径都不会强制重启。

自动检查的网络错误只写入持久桌面日志，不打断用户工作。手工检查或用户已选择的下载若失败，则会显示原生对话框并提供公开 Releases 页面。与生命周期无关的控制器持有重复操作抑制和用户决策；Electron 适配器持有传输事件，主进程持有原生展示。

### 发布更新源

每次稳定版 `desktop-vX.Y.Z` 构建都会为 arm64 和 x64 分别生成经过签名和公证的 DMG，以及 ZIP 与 blockmap。发布工作流保留 electron-builder 按架构生成的元数据，校验其中的版本与必需的架构标记 ZIP，再合并成一份 `latest-mac.yml`。合并后的更新源保留两种文件哈希，使 MacUpdater 能选择当前运行架构。客户端看不到 Release 草稿；维护者手工发布已审查草稿时，稳定更新源才会启用。应用只包含公开仓库身份，不包含 GitHub token。

桌面应用与内置 DSH 运行时会作为一个经过配套测试的应用单元一起更新。定时工作流观察上游 `dsh-v*` 标签，推送下游审查分支，并创建带预填 PR 链接的跟踪 Issue；它不会创建或合并 PR、修改桌面版本、创建标签或发布更新。仓库级 Actions 权限保持默认只读，该工作流只取得限定范围的分支与 Issue 写权限。这样，上游版本提醒与维护者的兼容性及发布决策保持分离。

### 安装时关闭

立即安装和退出时安装都会使用与普通退出相同的有界后端关闭路径。主进程先 dispose（资源释放）更新定时器，停止本地 DSH 进程树并关闭日志，随后才把已缓存的签名应用交给 Squirrel.Mac。第二次退出事件看到后端已经停止，可以继续退出且不会重复清理。

## 考虑过的备选方案

**在后台下载所有更新并自动重启。** 这样点击次数最少，但会在未经同意时占用带宽，也可能终止正在运行的本地工作。两次显式决策既让检查保持低打扰，也把中断时机留给用户。

**只更新内置 Harness 包。** 这样会产生一套桌面发布从未构建、签名或测试过的应用组合。整包替换让 Electron 代码、Web 资源、原生依赖与 DSH 运行时保持在同一个已审查版本上。

**使用私有仓库或需要认证的更新端点。** 分发到客户端的 token 可以从应用中提取，而要求每位用户配置 GitHub 认证又会引入与 DSH 无关的设置。公开仓库无需客户端凭据即可提供只读更新访问。

**为每种架构分别发布元数据文档。** MacUpdater 要求在发布 URL 上读取一份 channel 文档。确定性的合并过程会保留两份生成文件记录，并在创建草稿前拒绝缺失或架构标签错误的 ZIP。

## 验证

控制器测试会快照记录用户可见的下载与安装决策序列，并覆盖稍后重新进入、手工与后台错误、调度、开发构建提示和退出时安装。元数据测试覆盖确定性的双架构输出，以及版本、文件哈希和缺失架构拒绝。桌面 TypeScript 构建把 `electron-updater` 保留为打包后的 CommonJS 运行时依赖，两条打包冒烟测试路径都会通过发布的 Electron 可执行文件加载打包后的主进程模块图，再接受产物。发布 CI 还会在创建草稿前构建、签名、公证并检查两种原生产物。完整更新安装需要两个已签名公开版本，因此放在发布验收中验证，而不由无密钥源码测试完成。

## 后果

已安装用户可以感知更新并在安装前完成工作，公开发布页面仍是手工兜底。除 DMG 外，发布现在还包含 ZIP、blockmap 与 channel 元数据，因此发布时不得遗漏这些产物。维护者账号失陷仍是发布风险，所以 GitHub 审查、Apple 签名与公证、校验和、草稿审查、密钥扫描和私密漏洞报告继续作为相互独立的控制措施。桌面版采用上游 Harness 版本的时间会刻意延后，直到其 PR 与签名桌面版本都通过审查。
