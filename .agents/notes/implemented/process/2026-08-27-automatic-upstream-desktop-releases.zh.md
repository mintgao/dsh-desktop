# Agent Note: 自动引入上游并发布桌面版

Status: implemented

[English](2026-08-27-automatic-upstream-desktop-releases.md) | 中文

## 问题

DSH Desktop 是个人和小范围使用的发行版，明确选择跟随 DeepSeek Harness 的 Release。每次都要求维护者创建审查分支、合并、另选桌面版本、检查草稿再发布，会让常规引入依赖人的记忆和时间，与“复用每个上游 Release”的原则不符。流程仍然必须在真实合并或验证失败时停止，能够从中断的工作流继续，在问题版本公开后可以撤回而不抹除证据，并为另一台电脑或另一个 Agent 留下足够的持久状态。

## 决策

[`upstream-sync.yml`](../../../../.github/workflows/upstream-sync.yml) 每小时两次检查 `deepseek-ai/deepseek-harness` 的公开 Release。[`.github/upstream-sync-state.json`](../../../../.github/upstream-sync-state.json) 记录最近一次引入的上游标签、提交与发布时间，以及对应的下游桌面标签。初始记录指向下游已经包含的上游 Release 及其现有桌面版本，避免重新发布历史版本。工作流按发布时间排列公开且非草稿的 `dsh-v*` Release，每次只处理队首的下一个版本。手工触发可以选择这个队首版本，但不能跳过中间版本。

工作流取得准确的上游标签，把对应提交直接合入处于可发布状态的 `main`。推送前，它会安装锁定依赖，并运行桌面测试、桌面构建、仓库类型检查、文档检查和生成源码差异检查。发生冲突或检查失败时，工作流会在任何远端更新前停止，并创建或更新包含运行链接的 `Blocked: adopt DeepSeek Harness ...` Issue。维护者应在普通分支上解决这个准确版本的引入，通过正常流程合入修复，再重新运行工作流。

每个上游 `dsh-vX.Y.Z[-suffix]` Release 都映射为 `desktop-vX.Y.Z[-suffix]`。验证通过后，工作流会在一条专用引入提交中更新状态文件，创建带注释的桌面标签，并原子推送 `main` 与该标签。随后，它带着上游标签和提交显式触发 [`desktop-release.yml`](../../../../.github/workflows/desktop-release.yml)。显式触发避免依赖 GitHub token 推送去触发另一个工作流。发布工作流会检出标签，构建、签名、公证、检查并打包两种原生架构。上游驱动的任务会在所有检查通过后立即公开；预发布版标记为 Pre-release，稳定版成为 Latest。手工推送的桌面标签仍会为例外的桌面专用版本创建草稿。

原生发布构建完成前，引入提交和标签到达远端时状态就会推进。如果后续轮询发现记录中的桌面 Release 仍不存在，但桌面标签已经存在，引入工作流会识别这个中断状态；没有等价任务正在运行时，它会重新触发发布。记录中的桌面 Release 缺失时，它不会跳到更新的上游版本。

[`desktop-release-withdraw.yml`](../../../../.github/workflows/desktop-release-withdraw.yml) 提供可恢复撤回。它会把选定的公开 Release 转回草稿，同时保留原说明、标签与产物。撤回稳定版时，它会把剩余公开稳定版中最新的一个重新标记为 Latest。工作流会创建或更新 `Desktop release withdrawn: ...` Issue，记录每次撤回的原因和工作流运行、回退版本、恢复命令，以及“已安装应用不会被远程降级”这一事实。重新运行中断的撤回任务会补齐回退和缺失的 Issue 记录，但不会重复已经记录的运行。恢复时重新公开未改动的保留草稿；如果已经安装的应用需要实际降级，仍要手工用更早的 DMG 替换。

Git 持有每次源码变动和不可变桌面标签。状态 JSON 持有队列位置。生成的 Release 说明持有上游标签、上游提交和桌面源码提交。Actions 运行持有执行证据。阻塞与撤回 Issue 持有例外状态和恢复说明。这些记录，而不是上一段对话或某台机器的文件系统，组成另一位维护者或 Agent 必须读取的交接集合。本决策取代 [Mint 桌面下游开发](2026-08-24-mint-desktop-downstream-development.zh.md)、[公开桌面版签名](2026-08-25-signed-public-desktop-releases.zh.md)、[预览版手工更新提醒](../feature/2026-08-24-desktop-manual-preview-updates.zh.md)和[由用户控制的桌面版签名更新](../feature/2026-08-24-desktop-signed-auto-update.zh.md)中“手工审查上游、手工发布草稿”的部分；其中的仓库、签名、更新安装与用户确认决策仍然有效。

## 考虑过的备选方案

**为每个上游 Release 保留审查分支和手工草稿发布。** 这会提供两次人工暂停，但与“及时复用每个上游 Release”的既定原则冲突。源码与产物检查仍会阻止无效自动化，实际使用后发现的问题由撤回流程处理。

**只引入观察到的最新上游 Release。** 这可能静默漏掉中间版本，也会让历史映射含糊。每次只推进一个版本可以保留上游顺序，并为每次变动留下独立提交、标签、Release 与证据。

**版本有问题时删除 GitHub Release 与标签。** 删除会削弱审计，也会增加恢复难度。把 Release 转为草稿既能让公开发现失效，又能保留准确源码与产物。

**撤回后自动降级已经安装的应用。** 桌面更新器和 GitHub Release 通道都无法提供安全的远程卸载或降级操作。撤回会阻止新发现，恢复上一稳定版的展示；已经安装的回滚仍是明确的 DMG 替换操作。

## 验证

工作流测试会解析三份 Actions 定义，并要求有序 Release 状态、完整源码检查集合、`main` 与标签原子推送、显式发布触发、自动与草稿发布区别、签名与公证门禁、不删除标签的 Release 撤回、稳定版回退选择和持久 Issue 记录。文档检查会验证双语说明与 Agent Note。生产验收需要等待下一个真实上游 Release：引入任务必须更新状态与标签，发布任务必须公开签名产物与生成的来源记录，一次测试撤回与恢复必须在改变公开可见性的同时保留产物。

## 后果

常规上游发布不再需要维护者操作，并且每次成功引入都可以在 macOS 构建完成后对用户可见。这项选择明确用上游 Release 加自动合并、源码、签名、公证与打包检查来取代逐版本人工审查。与下游文件冲突或无法通过检查的上游变更会停止队列，并要求正常修复。Release 撤回快速且可恢复，但无法召回或远程降级已经安装的副本。仓库与 GitHub 记录为跨机器、跨 Agent 继续工作提供完整起点。
