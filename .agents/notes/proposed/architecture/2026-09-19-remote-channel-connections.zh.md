# Agent Note: 通过即时通讯平台的远程通道连接

Status: proposed

[English](2026-09-19-remote-channel-connections.md) | 中文

## 问题

桌面客户端把 agent 绑定在它所运行的机器上。想启动一个任务、回答一次权限提问、或读一个结果，用户必须在那台机器旁边，而产品没有任何手机能够触达的界面。

有两个即时通讯平台能在不需要公网入口的前提下承载这个界面。微信 iLink 机器人 API 是客户端自己驱动的 HTTP 长轮询，飞书的长连接是客户端打开的 WebSocket。两者都不需要入站可达性，这正是它们能被一个位于家用路由器之后的桌面应用使用的原因。

客户端不能做的，是为那些本已只存在一份的工作长出按平台复制的版本：把外部触发变成持久 Session、授权一个发送者、派发一条命令、转发一次权限提问。上游的 webhook 入口持有接纳事务的唯一实现，它归上游所有，而把那段顺序再实现一遍，就等于多了一处会把微妙之处做错的地方。

## 提案

把该能力作为一个完整的能力接缝交付：`packages/channel/channel` 中的服务定义声明 `ctx.channels`，每个平台一个服务提供方，以及一个把入站消息接纳为 Session 的消费方。持久契约——注册表接口、接纳事务的抽取、绑定的持久性、来源标注、投递、命令、权限转发、传输约束、打包、恢复，以及每个包的所有权——由[决策记录](../../../../docs/decisions/0001-remote-channel-connections.zh.md)决定。本笔记承载的是接缝为何长成这样，以及它放弃了什么。

阶段一交付接缝、`channel-session`、微信提供方、会话命令、权限转发、Remote 控制器与客户端设置区。阶段二在同一接口之后加入飞书；它的打包方式留给它自己的就绪记录决定。

### 接缝拓扑

`ctx.channels` 是一个注册表，而不是每个平台一个服务，因为枚举提供方的消费方需要一个单一的枚举点，并且不能按平台身份分支。提供方在发布之前完成认证与归一化，因此平台原始字节永远不会到达消费方，一个解析缺陷也不会变成一个 Session。

消费方是一个包，而不是每个平台一个：绑定、发送者授权、待处理请求记录、两档命令、投递记录与权限转发都与平台无关，把它们放在一处正是让第二个平台变得便宜的原因。

客户端界面是一个经 Remote 控制器投影的设置区，提供方走它，而不是各自发布自己的页面。

### 接纳事务的抽取

`packages/webhook/webhook/src/session.ts` 持有那个把外部触发变成持久根 Session 的事务的唯一实现，包括它的顺序与它的回滚。本次交付把最小的可复用服务抽到 `packages/session/session-admission`，它只拥有那个事务、别无其他；`channel-session` 从一开始就采用它，上游 webhook 在一个单独的工作项中迁移，其落地取决于上游评审。

由此留下的重复窗口就是代价。一套跨包对等套件把它限定住：让未改动的上游事务与抽取出的服务跑在同一组断言上，于是分歧会让一个测试失败，而不是让用户的会话失败。

### 配置

每一个随部署而变的值都是可从 `cordis.yml` 更改的、经校验的 `Config` 字段：轮询与重试边界、退避、限流策略、熔断阈值、分片上限，以及投递记录的保留期。协议常量、平台长度限制与安全不变量固定在提供方中。Mint bundle 只携带 patch 行，并以产品默认值启用该接缝；一个普通 Web 组合在没有这些默认值的情况下也能启动同一接缝。

## 考虑过的替代方案

**每个平台一个服务（`ctx.channelWeixin`），按约定发现。** 否决：没有单一枚举点，消费方要按平台身份分支，且第二个提供方意味着第二份契约。

**复用 `ctx.webhook` 并增加一种 channel 提供方类型。** 否决：webhook 入口适配的是一次性的"投递即触发 Session"，而不是连接生命周期、出站发送与按会话的绑定；它同时还是上游拥有的代码。

**发布平台原始入站事件，由消费方负责认证。** 否决：它把按平台的验证搬进共享代码，并把一个解析缺陷变成 Session。

**让每个提供方各自调用接纳。** 否决：它复制了一段恰好在最容易做错的地方最微妙的顺序，而其失败模式是泄漏一个仍在运行的 Agent。

**在本次交付内部复刻接纳事务，而不是抽取它。** 否决，理由同上；而且它会与上游实现分叉，却没有东西能发现这一漂移。

**等上游先暴露接纳事务再开工。** 否决：它把一个没有 webhook 可见效果的变更的功能进度，绑在上游评审上。

**让每个提供方拥有自己的客户端页面。** 否决：它成倍放大第二个平台必须构建的界面，并让设置体验无法收敛。

**复用 `MessageSourceMap` 的 `webhook` 成员并塞入 channel 形状的载荷。** 否决：它要么错述 `deliveryId` 与 `ruleId`，要么为每个消费方放宽它们，而桌面的来源投影恰恰需要这些 channel 字段来渲染那个标记。

**在一个会话中把并发的权限提问排队。** 由产品负责人否决：一个无人应答而落空的提问会以 `unavailable` 结算并拒绝，从而让用户从未看见的任务失败。

**为会话创建的 Session 设置显式标题。** 否决：它会让远程 Session 与桌面 Session 分叉，而后者已经由组合的标题能力从第一条消息命名。

**飞书与微信在同一阶段交付。** 推迟，而非否决：微信的协议是两者中更小、更容易验证的那个，而接缝正是第一个平台被验证之后让第二个平台变便宜的东西。

## 验收标准

表示完成的可观察状态，就是已接受的 brief 中位于 [docs/work-items/20260919-remote-channel-connections/brief.zh.md](../../../../docs/work-items/20260919-remote-channel-connections/brief.zh.md) 的 AC-1..AC-11；本笔记不新增自己的标准。交付必须通过的闸门记录在那里以及决策记录的打包章节中：装配的运行时闭包检查、打包后的冒烟测试、无密钥浏览器场景、跨包对等套件，以及顶层文档、类型检查与覆盖率闸门。

## 风险

**在迁移落地之前，存在两份接纳实现。** 对等套件是让两者保持一致的唯一东西，而一个它没有断言的平台特定分歧会到达用户。

**两次相邻持久写入之间的一次崩溃会孤立一个 Session。** 它保持挂在 Workspace 上、可从桌面读取、且从会话无法到达。没有任何原语能在一次事务中跨越 Workspace 注册表与存储域，因此这个窗口是被接受而非被关闭的。

**令牌锁是机器本地的。** 每个身份在每台机器上只服务一个已连接客户端，而第二台机器轮询同一身份会分流消息，且没有锁能阻止它；那里唯一的强制点是平台本身。

**被转发的权限提问是一个真实的执行边界。** 会话的权限预设是在设置时被显式选择的，并保持可见；而沉默以拒绝结算，因此一个无人应答的提问可以让任务失败。

**重复回复是可能的。** 至少一次投递是刻意的选择，因为丢失一条回复比重复一条更糟。

**平台会话会过期。** 一个被平台作废的微信会话需要重新扫码，没有任何重试策略能让它复活。
