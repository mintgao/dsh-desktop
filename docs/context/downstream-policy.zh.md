# DSH 二次开发规范

[English](downstream-policy.md) | 中文

## 目的与范围

DSH Desktop Mint 是 DeepSeek Harness 的下游桌面发行版。本规范约束现有功能、修复、进入产品的实验以及所有未来需求。当前已批准的两项产品需求是桌面客户端，以及让桌面用户发现、获取和应用 DSH 更新。新增产品目标必须明确决定是否纳入范围；支撑设施必须说明它服务于哪项需求。

## 插件职责

- 通过文档化的服务、事件和 UI slot，将 DSH 行为实现为可独立配置和释放资源的 Cordis 插件。复用 DSH 的 Agent（智能体）运行时、会话语义、权限和 Web 客户端。
- Mint Bundle 只负责插件选择和产品默认值。品牌、发布渠道和发行版身份不得进入通用插件。共享包不得按 Mint 身份分支。
- 原生代码负责应用、窗口、菜单、安装器、更新器和后端进程生命周期，不得重新实现 Agent 或 Session 策略。DSH UI 需要原生权限时，通过范围明确、具有类型定义且提供方可替换的能力接入；不得在可复用 Client 插件中导入 Electron。
- 缺少扩展点时，先定义最小的可复用 DSH 扩展，再由功能消费它。无法避免的上游改动必须单独记录理由、兼容性测试，以及回馈上游或移除的路径。

## 复用与兼容性

每项新增能力都必须指出对其他 DSH 开发者的具体价值和交付形式：可安装插件或 Bundle、可替换原生适配器，或者可复用的构建与发布工具。原生与发布设施无需伪装成运行时插件，但必须分离可复用行为和 Mint 配置。抽取程度由真实使用方需求决定，不能以复用为由建设泛化平台。

功能记录必须说明用户结果、所属包或原生模块、扩展点、状态与资源释放责任方、产品配置、权限、模型可见影响、支持的 DSH 版本及复用方式。包与发布者身份必须准确；本地 workspace 包不构成公开发布或外部安装的证据。

共享功能必须在不含 Mint 默认值的独立兼容 DSH 组合中通过验证。可分发包还必须通过外部打包安装测试，不依赖本仓库源码别名或 workspace 解析。兼容性声明必须列出实际测试的版本或范围、必需提供方、宿主与平台限制、数据格式限制及不支持的情况。上游的开发者预览声明不能免除这些责任，也不代表兼容任意版本。

## 更新与用户数据

上游发现、源码采用、合格桌面版本发布、用户安装是不同的完成结果。上游存在版本不代表桌面更新可安装。工作流成功或已派发发布任务，本身都不能证明交付完成。

无论改动来自 DSH、插件还是桌面功能，普通用户都只接收一个客户端更新，面对一个桌面版本和一次安装选择。默认更新界面说明用户可感知的改进与必要操作，不要求用户区分或管理组件版本。确切组件版本保留在发布元数据中，供维护和排障使用。

每个可安装版本必须标明桌面版本、确切 DSH 源码与版本、所含插件版本、支持架构、产物完整性与信任状态，以及相关数据兼容性。安装始终由用户选择。失败必须保留可用的已安装应用，或提供明确恢复路径；替换应用文件不能证明旧运行时可以安全读取新用户数据。没有场景证据，不得自动降级数据、静默执行破坏性迁移或宣称支持回滚。

更新设施必须有文档化的负责人、有界重试策略、可见阻塞原因，以及经过验证的恢复步骤。正确性和可维护性共同构成验收标准。增加自动化和权限必须解决已观察到的运维问题，并保留失败后的恢复路径。

## 审查与验收

每项改动都必须核对所服务的产品需求、插件职责、外部复用途径、版本兼容性和完整用户场景。代码存在、单元测试和配置检查不能替代相关的打包客户端、原生权限或真实升级场景。必须明确记录未验证的声明和阻塞前提。已有偏差必须登记，并在相关工作扩大偏差前评估；本规范不授权无关的全仓库重写。
