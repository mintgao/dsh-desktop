# 审核桌面端跨版本追赶交付

[English](catch-up-desktop-delivery.md) | 中文

## 概述

显式追赶升级通过一个 PR 采纳多个已审核上游版本，并交付一次桌面更新。[已接受决策](../decisions/20260910-desktop-catch-up-delivery.zh.md)规定源码历史、兼容性和发布权限。合并与发布仍需分别批准。

## 选择与准备

除常规配置、源码锁、受保护基线、桌面版本和输出参数外，`adoption-plan` 命令还要求 `--kind catch-up`、`--target-tag`、`--target-commit`、`--assessment` 和 `--baseline`。评估路径相对于仓库。完整的 `--fixture` 可离线验证选择；夹具不授予机器人最终写入权限。[CLI 集成测试](../../scripts/desktop-delivery/tests/operations.spec.ts)在临时 Git 仓库和读取适配器中执行完整参数集。

目标必须跨越源码基线之后至少两个选定版本。源码基线必须与已验证的公开桌面最新交付或已激活旧版基线一致。规划保留所有已记录观察；采纳区间止于显式目标。定时发现仍报告紧邻后继版本。身份缺失、标签变化、重复观察或尚未发布的源码推进会阻止准备。

发生冲突时，`adoption-prepare` 保留隔离检出目录。创建种子前，已审核评估及其所有引用文件必须存在于该目录；文件缺失会阻塞，直到维护者提供已审核字节并重新准备。每个选定上游提交都必须是目标的祖先。候选检查不持有写入凭据。拟议锁文件与种子保持分离。

维护者审核并推送精确种子。受保护主分支的可信工具执行 `adoption-apply`，独立读取完整实时观察及精确种子文件，生成仅修改锁文件且只有一个父提交的机器人最终提交。匹配的重试不写入。人工修正需要新的已审核种子；范围或评估字节变化需要新计划。

## 评估字段

版本 1 评估包含 `schemaVersion`、`from`、`to`、`releases`、`edges` 和 `directUpgrade`。每个版本使用锁文件中的精确 `id`、`tag`、`commit` 和 `publishedAt`。`releases` 是从 `from` 之后到 `to` 的有序区间。`edges` 为每一对相邻版本提供一个场景；`directUpgrade` 单独覆盖已安装基线到目标的升级。

每个场景包含 `from`、`to`、`status`、`persistedFormatsChanged`、`unsupportedDowngrades`、`compatibilityFindings` 和 `evidenceReferences`。状态为 `verified`、`blocked` 或 `unverified`。发现和降级限制是非空文本数组。每个证据引用包含仓库相对 `path` 和精确文件的 `sha256`。引用是普通叶子文件；自引用、源码锁引用、路径穿越、符号链接和冲突摘要均被拒绝。

准备阶段保留真实的受阻、未验证或格式变化评估。生产资格认定要求每条边和直接升级都已验证，并在安装经单独审核的迁移资格认定前拒绝持久化格式变化。边覆盖或全新安装不能证明直接升级兼容性。使用可丢弃副本；不得对用户真实主目录进行评估。

## 资格认定与恢复

新的源码最终提交使用 schema 3，始终包含 `catchUp`，其值为 null 或精确范围与评估身份。历史 schema 1 和 2 在受支持位置仍可读取。同上游修复、替代发布和人工重新最终提交保留现有追赶来源记录。普通推进输出 null，并保留紧邻后继语义。

新的生产清单使用 schema 2，包含规范化锁的 `catchUp`。其精确文件清单将评估及叶子证据作为平铺的 `catch-up-<path-sha256>.bin` 资产保留。校验器重新计算这些资产摘要，并比较清单与锁证据。范围资产缺失、多余或被修改会阻止资格认定和发布。历史 schema 1 清单不能授予追赶权限。

发布规划、标签及草稿准备、发布阶段独立验证实时区间与最新交付。固定目标之后的新版本不会扩大采纳范围。撤回可隐藏身份精确的受损版本；恢复要求保留的精确字节和祖先证据，不创建新采纳。自动降级不受支持。

## 可信部署

先通过旧可信路径，在当前上游身份上用 desktop 类型策略 PR 安装工具。所有者合并后，兼容工具进入受保护主分支，才准备实际追赶 PR。该工具前提不会发布中间桌面版本。候选工具和历史引导例外不能完成追赶最终写入。
