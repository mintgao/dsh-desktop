## 授权与范围

所有者确认已对齐项目并请求实现。本工作实现[桌面交付设计](../../decisions/20260908-desktop-update-delivery.zh.md) 的第二迁移阶段：可执行的发现、源码与版本检查、预览产物验证，以及面向维护者的只读试运行摘要。它提供启用替代远程写入者前必需的本地和 CI 证据。这是实现授权，不授权合并、发布、发送通知、改变 GitHub 保护或凭证，也不授权替换已安装客户端。

[二次开发规范](../../context/downstream-policy.zh.md) 约束所有新增能力。普通用户保持统一整客户端更新。维护者接受 Agent 辅助决策，以及 GitHub 通知与可选邮件；本阶段生成并验证通知内容，但不发送。替换生产信任模型仍是独立决策；本阶段无写入，既不需要也不授予该权限。

## 验收标准

- SH-1：可执行发现路径接受显式发行版配置，只读查询上游公开版本身份或使用所提供的离线 fixture（测试前置数据），产生确定性的下一个版本或阻塞输出；测试重复、改变及缺失身份。
- SH-2：源码锁定记录和候选元数据绑定确切上下游版本及组件版本；workspace 版本不一致时，在昂贵打包前拒绝。候选不能因发现成功就声称已采用或发布。
- SH-3：显式验证路径检查未签名预览产物完整性、架构、大小、摘要和确切候选的验证证据；单架构失败或缺失阻止整体成功。拒绝被修改或替换的文件。
- SH-4：选择启用的试运行工作流执行实际脚本和现有桌面构建打包路径，不依赖旧状态、App 或 Apple 凭证，不含仓库变更命令；正常运行不创建 PR、Issue、分支、标签或 Release。输出只包含工作流摘要和验证产物，绝不是生产发布回执。
- SH-5：摘要向维护者说明下一步、就绪或阻塞状态、证据和候选身份；相同工具通过另一发行版配置的测试。现有桌面更新行为和插件组合保持不变。
- SH-6：针对性开发测试、可执行 fixture 运行、适当本地打包证据、文档和独立 QA 证明已实现范围；准确报告未执行的双平台、原生或生产场景。
- SH-7：真实打包后端的认证就绪 URL 能传入桌面且不丢失令牌；拒绝无效远程来源，常规后端诊断脱敏令牌。原生解析器所有权仅限真实 DMG 冒烟失败所触发并经过审查的修订。

## 职责与计划

Tech Lead 编写附加决策，由另一位审查者批准。就绪后，一个 RD 写入者负责新交付脚本、测试、新试运行工作流及必需集成。协调者负责决策、工作项文档和双语对应侧。QA 负责最终独立验收，并对未变化候选执行一次完整配置默认验证。现有无关工作树修改保持不变。

使用现有源码构建桌面暂存流程，实现最小完整路径。不得为本阶段重构原生外壳或建立通用发布框架。只允许新增工作流；生产采用、发布、撤回、策略证明和控制保持不变。新的长期技术选择须在修改相关实现前交由技术作者与审查者处理。
