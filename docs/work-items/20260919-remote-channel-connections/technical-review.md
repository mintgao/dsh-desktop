## Findings

1. **Section 2, failure and rollback.** The sentence "failure before step 6 leaves nothing to roll back" is not faithful to `packages/webhook/webhook/src/session.ts`. Its catch block attempts `handle.dispose()` on every failure after `ctx.agents.create` returns, including the abort check between creation and attach where `attached` is still false; only detach is conditional on `attached`. A service implemented to that sentence leaks a live, published Agent on a pre-attach failure, and the non-regression list does not cover it. Resolve by stating the rule as: any failure after the Agent is created attempts Agent disposal; Workspace detach is attempted only when attach succeeded; the two are independent; rollback failures are logged and never replace the original error; the original error is rethrown.
2. **Section 2, the duplication window.** "The service's test suite … pins both implementations to one observable sequence" is unsupported as written, and the window is not bounded. The mitigation holds only if the new package's suite also executes the unchanged upstream `createWebhookSession` against the same assertions; the record does not say the suite reaches it or where that cross-package test lives, so upstream drift in `session.ts` goes undetected — the exact risk that motivated rejecting option (c). The bound is an unnamed follow-up work item that appears in no phase, and its landing depends on upstream review, the same dependency option (a) was rejected for. Resolve by stating that the suite drives both implementations and where it lives, naming the follow-up work item and its trigger, and stating the migration's upstream dependency.
3. **Section 2, the closing guarantee.** "The operation never returns a session id it did not admit, and a caller that received an error must not persist a binding" contradicts step 7, where the caller persists the binding inside `onAttached` after durable attach, and step 9, where admission can fail afterwards. The hook receives the session id before admission, and an error at steps 8 or 9 arrives after the caller has persisted. Resolve by specifying the compensation contract, or by stating that section 3's "missing Session means unbound" read rule is the only treatment, and rewording the guarantee to what is enforceable.
4. **Section 3 against section 6.** "`/new` removes the binding before it acknowledges" conflicts with the record's own fields and with section 6's "the next ordinary message creates the Session". A removed record leaves the next message with no authorized-sender set, so who may create the next Session is undefined, and no workspace or preset values to create it with; AC-4's workspace and preset display has nothing to show. Resolve by stating that `/new` clears only the session association (`sessionId` and `lastAdmittedMessageId`) and retains configuration and authorization, or by naming where those values persist across `/new`.
5. **Section 3, the redelivery claim.** "A crash before admission causes platform redelivery, and the durable binding makes the redelivery continue the same Session instead of creating a second one" is false for a crash between attach at step 6 and the binding write at step 7: no binding exists yet, so redelivery creates a second Session and the first stays attached to the Workspace, readable but orphaned. Resolve by scoping the claim to crashes after the binding write and stating the accepted orphan window, or by closing it.
6. **Section 2, the operation signature.** The stated interface omits three inputs the transaction needs: the session-id brand prefix, which the same section says the service takes as a parameter; the follow-up message and its source, which `session.ts` builds from the delivery and rule id inside the transaction, so the service must accept the source or a message constructor to preserve provenance; and the error-message subject, because validation messages read `webhook Session request <field> …` and the non-regression list requires validation errors and field names not to regress. Resolve by stating the full operation signature.
7. **Section 10, the token lock.** The lock names no medium and no scope (in-process, cross-process, or cross-machine) and no stale-lock recovery. Disposal releases the lock, but a crash does not run disposal, so a stale lock either blocks a legitimate reconnect or must be overridable; the record asserts a lock that "fails loudly" without stating either. Resolve by naming the medium, the scope, and the stale-lock rule, or by stating that the platform is the enforcement point and the lock is best-effort in-process.
8. **Section 7, the answerer seat.** "It answers only for agents whose Session is one of its bound Sessions … the approval seam's ownership rule holds" is asserted, not established. The record never states the seam's ownership predicate, and section 2 step 9 says the Agent is lifecycle-owned by `ctx`, which would contradict a lifecycle-based predicate. The reviewer could not establish from the handoff evidence that a channel-session answerer is entitled to answer at the seam. Resolve by stating the seam's ownership predicate and how channel-session satisfies it, verified against the approval subsystem before implementation.
9. **The pending-request list.** The brief requires unauthorized refusals to be diagnosable and to appear in a pending-request list the page renders and can approve, but neither section 3's record fields nor section 12's table names that list's owner, store, retention, or disposal. An in-memory list would silently drop pending requests on restart. Resolve by naming the store and its owner and disposal, or by dropping the approvable-pending-request path.
10. **Readiness release.** The brief's readiness record still read `decision-required` with no decision owner, no governing decision, `not-required` review, and the earlier blockers when this review ran, so the gate could not be released; the reviewer listed the exact conditions to satisfy. Because this review returns `changes-required`, the gate stays blocked and the revised record must be reviewed again before confirmation. The record's Open questions also named a product decision the brief did not resolve, which the contract fails closed on.

## Second review

Reviewed revision: the record after sections 2, 3, 7, 10 and 12 were rewritten to resolve the first review's findings.

Result: `changes-required`. The reviewer found findings 1 through 9 genuinely resolved with the specificity the first review demanded, and four defects in the revision's own new material.

1. **The compensation over-deletes.** "When the operation rejects after `onAttached` ran, `channel-session` deletes the binding record it wrote there" is correct only when this transaction created the record. On a re-admission after `/new`, or after the bound Session went missing, the record pre-exists, and section 3 requires every other field to be retained; a literal deletion discards the workspace, presets, authorized senders, display options, and cursor. Resolve by restoring the record's pre-write state, and deleting only a record this transaction created.
2. **The optional title against the webhook's required title.** The signature and step 1 make `title` optional, but upstream `session.ts` requires it and the non-regression list promises the validation errors and field names survive the migration, so the missing-title error cannot be produced by the specified contract. Resolve by stating who raises it on the webhook path, or by narrowing the claim.
3. **The approval write path.** Approving a pending request adds a sender id to the binding record, which has several writers — the admission transaction's `onAttached` write, `/new`'s clear, the cursor and `lastAdmittedMessageId` advance, and the approval itself, which is two writes. No serialization is stated, so a read-modify-write can lose a concurrent admission write. Also undefined: approval for a conversation with no binding record yet, because a refused message creates no Session. Resolve by naming the write discipline and the no-record case.
4. **The stale-lock double-poller window.** The heartbeat refreshes once per poll cycle while the stale threshold equals the configured poll bound, so a live holder whose poll overruns the bound can be overridden by a second instance sharing the store, and no superseded-holder stop rule is stated. Two pollers can coexist, which is the split-message failure the lock exists to prevent. Resolve with a threshold carrying margin over the poll bound, and a superseded-holder rule that stops polling.

Precision notes, non-blocking: "a failure at or after attach detaches" can be read to include a failure inside the attach call, where `attached` is still false, while the exact rule is that detach is attempted only when attach succeeded; the claim that no primitive spans the Workspace registry and the storage domain in one transaction is an evidence-limited assertion rather than a verified one; and attributing the answerer predicate to `packages/interaction/user-approval/src/index.ts` over-attributes, because `scopeTarget`'s admission semantics live in `@deepseek-ai/dsh-scope`.

Nothing in the record remains an unresolved product-owner decision. The only deferral is the Phase 2 Feishu packaging choice, which the record explicitly leaves to that phase's readiness record.

Limitations: the read-only perspective is instructed, not enforced by a sandbox, and independence from the author and revision instances is not sandbox-proven. The review was limited to four files, so the `scopeTarget` admission semantics, the storage-domain transaction capabilities, the brief's readiness record, and the existence of the named follow-up work item and parity test were outside the read set; the orchestrator's two mechanical changes were taken as given.

## Third review

Reviewed revision: the record after the second review's four defects and three precision notes were fixed.

This review was split between two independent instances, because one reviewer reading the whole record plus its code evidence exceeded the host's per-run budget. One instance covered section 2 against `packages/webhook/webhook/src/session.ts`; the other covered sections 3, 7 and 10 against `packages/storage/storage-domain/README.md`. Each received only its own sections, extracted verbatim from the persisted record, and neither saw the author's reasoning.

Result: `approved` on both parts.

Section 2: approved. The compensation branches correctly — deletion only for a record this transaction created, restoration of the pre-write state when the record pre-existed — and the no-live-Agent guarantee is marked best-effort, matching the code's independent detach and dispose attempts with a logged, swallowed rollback failure. The title arrangement was verified against the code: `resolveRequest` runs synchronously before any await and still enforces `workspacePath`, `title`, `prompt`, `agentPreset` and `permissionPreset` with the existing error text and field name, so the webhook contract survives, and the service's reduced required set keeps everything the transaction consumes. Both precision notes are addressed: a failure inside the attach call leaves `attached` false, and the transaction-span assertion was removed rather than kept as a fact. The ordering list tracks `session.ts` step for step and the rollback rule matches it exactly. The reviewer could not verify the forward-looking references — the parity test and the follow-up work item — from a two-file read, and recorded that they neither contradict the code nor overclaim.

Sections 3, 7 and 10: approved. The write discipline was verified against the storage domain's README, which documents one per-domain write chain whose `update` transform runs at its slot so concurrent updates never interleave, and which lists `missing-key` as exactly an update on an absent record. Creation at setup was found consistent with the later `onAttached` sentence. The stale-lock threshold of twice the poll bound was found coherent with a per-cycle heartbeat and to close the original window. The section 7 attribution correction is reflected.

Two items the third review left open. The crash-window sentence's phrase "has no binding yet" can be misread as "no record", although the behaviour it states still follows; this is phrasing, not a defect. The lock's cross-process scope depends on the storage subsystem providing cross-process reads, which that package's own single-process change-visibility limitation contradicts; the reviewer recorded it as not establishable from two files, the orchestrator then verified the contradiction against `packages/storage/storage-domain/README.md`, and a correction to section 10 was reviewed before the gate was released.

Limitations: each reviewer's read-only perspective was instructed, not sandbox-enforced, and independence is not sandbox-proven. Each was limited to two files, so code-level assertions outside them and the existence of the named follow-up work item and parity test were not independently checked.

## Verification of the section 10 correction

Reviewed revision: section 10's token-lock paragraph after it was corrected to an OS-level lock file created with an exclusive-create flag, with section 12's row updated from the token-lock record to the token-lock file. A separate instance reviewed the corrected paragraph with the text inlined and no file reads.

Result: `approved`. Atomic `O_CREAT|O_EXCL` on a local filesystem genuinely excludes a second process on one machine, so the stated scope and its not-cross-machine limit hold; cross-process readability is what enables the heartbeat and holder-id observation the stale and superseded rules use. The per-cycle heartbeat with a threshold of twice the poll bound leaves one bound of margin, which covers an overrun of up to one extra bound, and a longer stall is resolved by the superseded-holder rule after one overlap cycle. Nothing in the paragraph depends on the storage domain or any in-process-only mechanism, and no claim exceeds what a machine-local file lock delivers.

The review recorded three bounded races to pin at implementation: the override's atomicity, so two concurrent overriders cannot both believe they hold the lock; the lock-check cadence, so a superseded holder does not poll once more; and the heartbeat write path once an override replaces the file. It judged them transient and self-resolving rather than decision-level defects.

Limitations: the review was design-level and read no files, so the configured poll bound and the override procedure cannot be verified until that code exists; the read-only perspective was instructed, not sandbox-enforced, and independence is not sandbox-proven.
