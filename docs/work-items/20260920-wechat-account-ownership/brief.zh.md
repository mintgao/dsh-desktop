## Goal

一个 DSH Desktop Mint 组合同时服务多个微信号，平台的一条连接一个账号规则由此成为明确、可逆的归属选择，而非静默接管。把某个微信号连接到 DSH 的用户，在扫码之前就能看到这一步会断开该账号上的其它助手；账号被夺走的用户能看到是哪个账号、是平台夺走的，以及夺回来的那一个动作。第二个账号与第一个账号以同样的方式添加，且每个账号各自拥有其会话、Session 绑定与回复路径。

## Context

父工作项 [20260919-remote-channel-connections](../20260919-remote-channel-connections/brief.zh.md) 拥有通道 seam、其验收标准 AC-1..AC-11，以及构建消费方与微信提供方的 M1/M2 切片。其 brief 假定**每个平台一张卡片**，而 M2 切片正是这样实现的：一个固定身份 `weixin`、一条凭据记录、一个令牌锁文件。

于 2026-09-20 在真实平台上验证的事实，来自一次往返——其脚手架以真实传输层启动提供方，其扫码、消息与回复均由负责人完成：

- **一个微信号同一时刻只持有一条机器人会话。** 对该账号的扫码登录会替换前一个客户端持有的会话：被顶掉的客户端，其轮询与发送都报 `errcode -14`（`session timeout`），且不自行扫码就无法恢复。连接到同一账号的 Hermes 网关，在本提供方扫码确认后五秒记录 `Session expired; pausing for 10 minutes`，其出站重试也以同一错误码失败。
- **登录入口由平台选定。** 本提供方请求 `ilink/bot/get_bot_qrcode?bot_type=3`；对 `0`–`9` 全部探查后，除 `3` 以外的每个值都返回 `ret=2, invalid bot_type`，而它返回的二维码指向同一个 liteapp 入口。因此实现该 API 的每个客户端都扫进同一入口：独占性属于微信号本身而非某个客户端实现，两个客户端也无法通过选择不同入口规避。
- **微信会话保持不变。** 接管前后承载机器人的是同一条聊天；微信没有任何信号表明所连接的客户端发生了变化，因此产品是用户唯一能获知此事的地方。

设计必须承载的结论：拥有持久状态的单位是账号而非平台；每条连接注册的身份必须在重启后保持稳定；断开是一种用户必须能读到、也能逆转的状态。

## Scope

In:

- 一个组合中的多个已连接微信号：每个账号拥有各自的注册、凭据记录、令牌锁、轮询循环与会话绑定集合。
- 一个拥有账号集合与登录序列的包内服务，使添加账号不再依赖注册先行存在。
- 归属语义：扫码之前言明的接管、区分「连接期间被夺走」与「启动时已失效」的顶下线诊断，以及那唯一的恢复动作。
- 断开单个账号：停止它的轮询、释放它的锁、删除它的凭据记录，且不触碰其它账号。
- 启动时恢复全部已存账号，无需扫码。
- 治理决策记录的修订与包文档对。

Out:

- 让两个客户端在同一个微信号上并存。平台只暴露一个机器人入口，因此这在本仓库内不可达；产品改为言明该规则。
- 客户端设置分区。父工作项的 M3 切片拥有该页面；本切片只暴露它消费的读取与通告。
- 会话命令、权限提问转发、群聊、媒体，以及飞书提供方。
- 任何自动重新扫码、重连循环，或后台尝试夺回账号的行为。

## Acceptance criteria

- [ ] AC-1: 一个组合同时服务两个或多个已连接微信号；每个账号注册自己的通道身份，任一账号上收到的私聊消息都会在其账号身份下接纳出一个 Session，并通过该账号的提供方投递回复。
- [ ] AC-2: 每个持久化取值都归属单个账号：其凭据记录、令牌锁文件、轮询游标与会话绑定。断开其中一个账号只停止它的轮询、只释放它的锁、只删除它的凭据记录，且其它账号的记录保持不变。
- [ ] AC-3: 每个已存账号在启动时无需扫码即被恢复；平台会话已失效的已存账号报告需要重新扫码的状态，并且不进入轮询。
- [ ] AC-4: 添加一个账号是从 Host 界面驱动的一次扫码，无需编辑配置文件，且该账号以「扫码的微信号」派生的身份注册，并以该次扫码绑定的机器人身份作为展示名称。
- [ ] AC-5: 连接期间被平台夺走的账号，其诊断点名该次接管与那唯一的恢复动作，且该状态与「进程启动时已存会话就已失效」可区分。
- [ ] AC-6: 组合内没有任何东西自行夺回账号：没有自动重新扫码、没有对平台已夺走会话的重连循环，也没有同一账号的第二个轮询方。
- [ ] AC-7: 包文档为用户言明该平台规则：一个微信号同一时刻只服务一个客户端，连接即接管该账号，被顶掉的客户端需要自行重新扫码，且微信本身没有任何信号。

## Design and technical notes

### Identity

一个账号的身份是微信号本身，而不是平台为它签发的机器人。确认后的扫码会同时返回两者：`ilink_bot_id` 命名该次扫码创建的机器人，`ilink_user_id` 命名扫码的微信号。每次扫码都会铸造一个新的机器人，因此机器人身份是账号的展示事实、绝不是它的键；账号以用户身份为键。它注册 `ChannelId('weixin:<slug>')`，其凭据记录为 `channel-weixin/account-<slug>`，其令牌锁为 `weixin-<slug>.lock`，其中 `<slug>` 将该用户身份转为小写并把 `[a-z0-9]` 之外的每个字符替换为 `-`，从而同时满足注册表与凭据服务所强制的身份语法。

由于身份取自平台自身的取值，它在重启后依然成立，因此绑定到它的会话绑定、已授权发送者与游标始终挂在正确的账号上。该变换是有损的——两个不同的身份可能归约为同一个 slug——因此每条记录都在 slug 之外保留原始用户身份，而注册一个 slug 已被另一账号占用、原始身份却不相同的账号时，会被拒绝并给出诊断，而不是覆盖那条记录。

因此对同一个微信号重新扫码，会在同一身份下就地替换其登录产物：同一个账号、新的机器人、新的会话。由于注册身份是稳定的，这次替换是一次有序交接而非第二次注册：停止该账号的轮询、释放它的锁、释放它的注册，然后注册一个以新机器人身份作为展示名称的新提供方——注册表会拒绝同一身份下的第二个提供方，而新提供方也不该撞上前任的锁。当某条已存记录的载荷不可读时，其原始身份未知，slug 冲突便无法判定；此时对该 slug 的新登录产物会被拒绝，直到用户断开那个不可读的账号——这是失败关闭的读法。

注册的 `displayName` 携带该账号当前的机器人身份；卡片显示的平台标签由页面自行组合，因为客户端文案归语言环境所有。

### The account surface

添加账号不能是已注册提供方的方法，因为扫码之前并不存在注册。因此 `packages/channel/channel-weixin` 成为一个服务包：默认导出一个服务类，它拥有账号集合、登录序列与各项注册，并注入 `channels`、`credentials` 与 `channelSession`——每个账号的轮询正是从消费方的 `resumeCursors(identity)` 处恢复的。

- `accounts()` —— 每个已连接账号一项视图：其注册身份、平台机器人身份、连接状态与最近一次状态迁移。
- `beginLogin()` —— 启动一条扫码序列，替换任何已在进行中的序列，并返回该序列的状态。
- `cancelLogin()` —— 放弃一条进行中的序列；账号集合不变。
- `disconnect(identity)` —— 停止该账号的轮询、释放其锁、删除其凭据记录，并注销其提供方。

连接状态经注册表到达订阅方：每个账号的提供方以其注册的 `changed()` 通告，`ctx.channels.onChange` 将其带给控制器。登录序列没有注册可依附，因此该服务在自己的上下文事件上通告它，声明方式为合并进 Cordis 的 `Events` 接口——与 `packages/credentials/credentials/src/types.ts` 中声明 `credentials/record-updated` 的方式相同——并同样包容监听器失败。

### Durable state

- **每个账号一条凭据记录。** `credentialKey('channel-weixin', 'account-<slug>')`，保存扫码产生的登录产物以及 slug 所派生的原始用户身份。启动时枚举 `listRecords()`，保留 scope 属于本包且 id 匹配 `account-<slug>` 的条目，并读取每份载荷：可解析的记录会注册其账号并恢复其轮询；不可解析的记录会保留该记录，并把该账号注册为 `unavailable`，诊断说明已存登录不可读、重新扫码是恢复方式——因为静默跳过引用对象正是仓库快速失败规则所禁止的。来自被替换的单身份布局的键不是账号，不予接纳，并原样保留而非删除。该键的 id 段满足凭据语法（`^[a-z][a-z0-9-]*$`），这正是 slug 携带 `account-` 前缀的原因。
- **每个账号一个令牌锁。** `<lockDirectory>/weixin-<slug>.lock`，因此同一台机器上的两个账号永不争用同一个文件，陈旧规则也保持其按账号的含义。
- **陈旧阈值取最坏周期。** 只有当心跳早于所配置边界允许的最坏周期时，锁才算陈旧——轮询尝试次数乘以轮询超时，加上其间各次退避——而不是单个轮询超时的两倍；因为一个正在自身配置边界内重试的持有者，绝不能对第二个实例表现为已死。轮询只在所配置边界之内采纳平台建议的超时，因此该最坏周期单凭组合即可算出。
- **绑定与游标不变。** 消费方本就以通道身份为键，因此按账号的身份即可得到按账号的会话，`channel-session` 无需改动。

### Ownership and recovery

- 连接流程在二维码渲染**之前**言明接管：连接某个账号会断开持有该账号的其它客户端，被顶掉的客户端需要自行扫码才能回来，而微信对发生此事没有任何信号。措辞由页面负责，依据是 Host 提供的事实。
- **区分两种失效。** 判据是本进程能够观察到的东西：该账号是否在持有这条记录期间完成过一个轮询周期。该时点之后的 `errcode -14` 报告为 DSH 连接期间被夺走的会话；之前的则报告为 DSH 启动时已不可用的已存会话——它很可能由别处的接管造成，但不作为接管来报告。一次以 `-14` 失败的发送会驱动同一个状态与同一条诊断，因此一个所有回复都发送失败的账号不会继续被报告为已连接。这两种读数共用同一个恢复动作，而诊断正是告诉用户「刚被顶掉」还是「看的是一个早已不在的账号」的东西。
- **没有自动恢复。** 对于平台已夺走的账号，没有重新扫码、重新轮询或重新注册。需要重新扫码的状态被如实报告，并在用户行动之前保持该状态。
- **断开对平台是诚实的。** 移除一个账号会停止 DSH 对该账号的使用并删除已存产物；它不释放平台会话，因为平台只会在另一次登录替换它时释放。卡片如此说明。

### Migration

没有任何已发布内容：M2 切片的单身份布局——一个固定的凭据键与一个固定的锁文件——不承载任何已发布数据，因此本次改动将其替换而非迁移。治理决策记录该替换，包的测试覆盖新布局而不是两者。

### Configuration

组合继续言明它已经言明的按账号边界：轮询与发送的尝试次数及退避、限流延迟、断路器阈值、分块长度与锁目录。账号集合是运行时状态而非配置，因此不新增字段，也不硬编码任何边界。

## Client experience

页面本身属于 M3 切片；本切片固定的是它所需的接口与陈述。

- **连接列表。** 每个已连接微信号一张卡片，而不是每个平台一张卡片：名称是机器人身份，加上 `StateDot`、工作区与权限 preset 摘要、已授权发送者，以及 断开连接。添加账号是同一分区上的独立动作，而不是某个已有卡片的一种状态。
- **设置弹窗。** 第 2 步「确认身份」承载归属陈述：该身份同一时刻只服务一个客户端，连接即接管该账号，该账号上的其它助手会被断开并需要自行扫码才能回来，且微信不会给出客户端已更换的信号。
- **被夺走状态。** 卡片显示诊断与一个动作，重新扫码接管；该状态在用户行动之前持续存在。
- **断开连接。** 确认文案说明 DSH 将停止使用该账号并忘记其产物，而微信会话本身不受影响。

## Risks and open decisions

- **该独占性是本仓库无法解除的平台规则。** 若 iLink 日后暴露第二个入口，并存将变得可达；此处的归属模型依然成立，因为它把账号当作归属单位，而不是假定永远只有一个客户端。
- **没有第二个微信号就无法演练两个真实账号。** 负责人稍后提供一个；在那之前，多账号行为以脚本化传输层证明，按账号隔离则通过真实组合测试证明。待完成的真实账号证据记录为本工作项验证记录中的一条验收项；它不阻塞实现，而 AC-1 由组合测试证明。
- **枚举会读到属于其它包的记录。** 提供方按自己的 scope 过滤；属于其 scope 内、载荷无法解析的记录会被报告为带恢复动作的 `unavailable` 账号，绝不丢弃。
- **M3 切片可能重塑该接口。** 若页面需要不同的投影，需要复查的就是这些读取；本切片不构建任何客户端代码。
