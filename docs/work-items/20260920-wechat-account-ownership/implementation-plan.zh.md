## Slice boundary

范围内：

- 按账号的身份 `weixin:<slug>` 及其派生的持久键。
- 拥有账号集合、登录序列与各项注册的插件内服务。
- 启动时枚举与恢复、断开，以及两种顶下线诊断。
- 包 README 对、决策修订与重新生成的目录。

范围外：

- 客户端设置分区（父工作项的 M3 切片消费本切片暴露的接口）。
- 飞书、会话命令、权限提问转发、媒体与群聊。

## Package shape

`channel-weixin` 成为一个服务包：默认导出即服务类，以 `ctx.channelWeixin` 注入，并为每个已连接账号注册一个提供方。

| 文件 | 职责 |
|---|---|
| `src/index.ts` | 服务：账号集合、`accounts()`、`beginLogin()`、`cancelLogin()`、`disconnect(identity)` 与各项注册 |
| `src/provider.ts` | 单个账号的提供方：`attach`、连接生命周期、发送路径、连接状态及其诊断 |
| `src/accounts.ts` | 由扫码产物的 `ilink_user_id` 派生的 slug、由它派生的凭据键与锁文件名、slug 冲突检查，以及已存账号的枚举 |
| `src/login.ts` | 扫码序列：获取、状态轮询、刷新，以及它产出的登录产物 |
| `src/lock.ts`、`src/poll.ts`、`src/send.ts`、`src/normalize.ts`、`src/abort.ts`、`src/transport.ts` | 机制不变，凡触及平台状态处按账号参数化 |
| `src/types.ts` | 类型，以及该服务的登录通告在 Cordis `Events` 接口上的声明 |

## Durable state

单个账号的状态，且不含任何其它账号的状态：

- 凭据记录 `channel-weixin/account-<slug>`，保存扫码产生的登录产物。
- 所配置锁目录中的令牌锁文件 `weixin-<slug>.lock`。
- 消费方按身份 `weixin:<slug>` 保存的会话绑定、已授权发送者、游标与投递记录。

与之前一样，本包不创建自己的存储域。

## Sequences

**添加账号。** `beginLogin()` 获取一个二维码并通告其状态；平台的应答驱动已扫码、已确认、已过期并刷新，或失败。确认后的扫码产出它创建的机器人（`ilink_bot_id`）与扫码的微信号（`ilink_user_id`）；账号以第二个为键，因此对同一微信号重新扫码会在同一身份下替换其登录产物，而与另一账号原始身份冲突的 slug 会被拒绝并给出诊断，而不是覆盖那条记录。对于已注册的账号，这次替换是一次有序交接——停止该账号的轮询、释放它的锁、释放它的注册、注册以新机器人身份作为展示名称的新提供方——因为注册表会拒绝同一身份下的第二个提供方，而新提供方也不该撞上前任的锁。对全新账号的确认且无冲突的扫码把登录产物写入该账号的键，注册提供方，并启动它的轮询。第二次 `beginLogin()` 会替换仍在进行中的序列；`cancelLogin()` 放弃进行中的序列，且不触碰账号集合。

**恢复。** 服务初始化时，枚举读取本包的 `account-<slug>` 记录、解析每份载荷，并注册每一个能读到的账号；属于本包 scope 内、载荷无法解析的记录仍会注册，状态为 `unavailable` 并带「已存登录不可读」的诊断——因为静默丢弃它会掩盖一个用户在平台上仍然持有的引用对象。来自被替换的单身份布局的键不是账号，不予接纳，且原样保留。

**顶下线。** 平台夺走会话时轮询报告 `expired`，而以同一错误码失败的发送会驱动同一个状态。提供方记录本账号是否在持有这条记录期间完成过一个轮询周期：该时点之后的诊断点名 DSH 连接期间被夺走的会话；之前的则点名早已不可用的已存会话。无论哪种，账号都保持注册、停止轮询，等待用户行动。

**断开。** 停止该账号的轮询、释放其锁、删除其凭据记录并注销其提供方。平台会话不被释放，卡片也如此说明。

## Configuration

不新增字段。组合继续言明它已经言明的按账号边界，而账号集合是运行时状态而非配置。

## Evidence this slice owes

- 每个模块的单元测试，`src` 下逐文件 100% 覆盖率：由 `ilink_user_id` 派生 slug 与键、slug 冲突拒绝（含载荷不可读时的默认行为）、按 `account-<slug>` 形态枚举与解析（含无法读取的载荷注册为 `unavailable`、被替换布局的键不予接纳）、服务的账号集合及其三项操作、重新扫码的有序交接顺序、提供方的 attach 与两种顶下线诊断、发送期的 `-14` 驱动同一状态、平台建议的轮询超时被收束到所配置边界、最坏周期的陈旧阈值，以及发送路径。
- 经由 Loader 的真实组合测试，两个账号：两者都注册，每个账号的一条入站消息在各自身份下接纳出一个 Session，每条回复经各自账号的提供方离开，且断开其中一个后另一个仍保持连接。
- README 对、重新生成的目录，以及 `pnpm run doc-sync`。
- 一次由负责人参与的两个真实账号往返，待存在第二个微信号后进行；在此之前保持未完成。

## Order of work

2. 从 `index.ts` 中提取 `provider.ts`，保持行为不变，并把既有测试移到它上面。
3. 服务：账号集合、`beginLogin`、`cancelLogin`、`disconnect`、登录通告。
4. 双账号 Loader 组合测试。
5. README 对、目录、`doc-sync` 与提交。

## Risks in this slice

- **包的导出形态改变**，因此所有既有测试在同一次改动中随之迁移；不存在半转换状态。
- **两个账号共享进程的定时器与传输层，但不共享状态。** 一个账号的登录产物泄漏进另一个账号的提供方，正是本切片的隔离证据要捕获的失败。
- **第二个真实账号由负责人提供。** 在此之前，多账号证据就是组合测试，而「两个真实账号」的验收标准保持未完成。
